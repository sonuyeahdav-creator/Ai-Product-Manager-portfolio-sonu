Evals

How I test AI output before I trust it

A demo shows the happy path. An eval shows what happens on the twelfth messy input. This page is the method I use, plus the one project where I can show the numbers.

Why it matters

The eval set is the product

An LLM feature fails quietly. A button either works or it does not. A model returns something plausible, the screen looks fine, and the error shows up three weeks later in a shortlist nobody can explain.

So I build a small set of real inputs, run every change against it, and write down each failure in a category. The category is the useful part. "It is unreliable" cannot be fixed. "The parser guesses when the resume has two columns" can be fixed by Monday.

Loop

Six steps, one day

Small enough to repeat every week. Rigorous enough to catch the failures that matter.

01

Collect real inputs

Twenty to fifty cases from production or from the client. Not synthetic examples I wrote myself.

02

Write the expected output

By hand, once. This is the ground truth. It is boring and it is the whole exercise.

03

Pick one metric per failure mode

Schema valid. Field accuracy. Grounded answer. Correct tool call. One number each.

04

Run and log

Every failure gets a category and the input that caused it. Keep the input file.

05

Fix the smallest thing

Usually the boundary between two steps, not the model. Re-run the whole set.

06

Ship the number

Put the pass rate in the release note. If it drops later, someone will notice.

Case

HIREin: parse, then score

A recruitment engine that reads a resume and scores it against a job description. The first version did both in one prompt.

What broke, and what fixed it

Real resumes, not demo resumes
Task
Resume in, structured JSON out, then a score against the job description with reasons.
Test set
Real resumes with two column layouts, tables, unusual headers, and inconsistent date formats. The kind of file a recruiter actually receives.
Failures
Five types, listed in the table below. The worst was not broken JSON. It was confident invention, where the model filled a missing field with a plausible skill.
Fix
Split parsing and scoring into two agents with a typed contract between them. Added retry on the parse step and a repair routine for trailing commas and unescaped quotes.
Result
100 percent JSON parsing reliability in testing. 1st place out of 60 teams at the Masai School x IIT Patna hackathon, pitched to senior PMs from Google Maps and Microsoft.
Tradeoff
Two calls cost more and take longer. A wrong shortlist is worse than a slow one.

Honesty

What is not measured yet

A public eval page is only worth reading if it says where the evidence stops.

Measured: HIREin parsing reliability, by hand, against a set of real resumes.
Not measured yet:
  • Skill extraction accuracy against a human labelled set. I know the JSON is valid. I do not have a field level accuracy number.
  • Whether the score agrees with a recruiter's judgement. That needs override data from real users.
  • The content agent and the video editor. Both are in use. Neither has a formal eval set.

I would rather write that down than put a fake percentage on this page.
Next

What I would build next

An override log

Every time a recruiter changes a score, store the before, the after, and the reason. That log is a free eval set, and it grows with usage.

  • Tracks agreement over time
  • Turns disagreement into a test case
  • Makes the model's opinion auditable

Evals in the release note

A pass rate next to the version number. If the number drops, the release waits. Same discipline as a test suite, applied to output that has no fixed answer.

  • One number per failure mode
  • Run on every prompt change
  • Failures linked to the input file
