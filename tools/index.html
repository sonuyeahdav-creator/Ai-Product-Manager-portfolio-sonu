HIREin: the design decision that mattered

One prompt that parses and scores looks efficient. It is also where reliability dies. So I split it.

The flow

Resume in, ranked shortlist out
01

Intake

Resume file or text lands on a webhook.

02

Parse agent

Extracts a strict JSON profile. No scoring, no opinions.

03

Score agent

Reads the clean profile against the JD. Returns a score and reasons.

04

Store

Writes to Supabase and returns a ranked view.

Problem
A single LLM call had to hold two jobs at once. It invented skills the candidate never had, and the JSON broke whenever the resume had an unusual layout.
Action
Two isolated agents with a typed contract between them. The parse step retries on failure. A repair routine fixes trailing commas and unescaped quotes before the score step ever sees the data.
Result
100 percent JSON parsing reliability in testing, after an eval set of real resumes and a failure log for every broken parse. 1st place out of 60 teams at the Masai School x IIT Patna hackathon, pitched to senior PMs from Google Maps and Microsoft.
Tradeoff
Two calls cost more and take longer than one. I took that trade because a wrong shortlist is worse than a slow one.
What I would change next. Add a human review queue between scoring and shortlisting, and log every override. That log becomes the training set for the next version of the scorer.
